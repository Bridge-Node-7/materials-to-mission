# Public Program Register

## Purpose

This register preserves the durable public-safe decisions and future options developed during
the Materials-to-Mission journey without turning the public repository into a transcript,
internal notebook, customer workspace, legal opinion, or enterprise operating manual.

Materials-to-Mission is maintained through the stealth personal GitHub account
`Bridge-Node-7` as an individual-scale public demonstration. It is not an organization
deployment or evidence of team adoption.

## Integrated Public Doctrine

The current public method preserves these durable decisions:

- local-first and no telemetry by default;
- synthetic public examples only;
- one canonical public schema authority;
- Decision Charter, Evidence Record, Material Assurance Record, and Decision Passport;
- visible unknown, unsupported, contradicted, expired, revoked, and superseded evidence;
- noncompensating critical conditions;
- deterministic validation, rendering, packaging, and release evidence;
- protected-content scanning and fail-closed behavior;
- named human ownership of every consequential disposition;
- no qualification, certification, compliance, adoption, production, or commercial claim;
- minimal website routing;
- Frontier Decision Engine as a possible later consumer, not a second schema authority.

## Evidence-Gated Future Options

These ideas remain available only when real use demonstrates the need:

1. Compare at least three materially different cases before stabilizing cross-case fields.
2. Build a thin Frontier Decision Engine adapter after Case 001 reveals a recurring browser
   or decision-workflow need.
3. Add evidence expiration, change events, supersession, and reassessment behavior when
   continuing-assurance use is demonstrated.
4. Add a guided Action Queue or browser intake only after repeated onboarding friction is
   observed.
5. Add CSV or spreadsheet import only after recurring customer-controlled format needs are
   established.
6. Publish a sanitized case study only after explicit technical, confidentiality, IP,
   security, export, and release authorization.
7. Consider an experimental Section 4872 readiness profile only after primary authorities,
   effective dates, acquisition applicability, exceptions, and human legal review are
   versioned separately.

A future authority profile must distinguish statute, published regulation, applicable
contract terms, Executive Order readiness planning, and internal recommendations. It must
treat FOCI and unreliable-foreign-supplier signals as review indicators rather than automatic
adjudications. It must not present generated templates as official filings.

## Private-Only Capabilities

The following belong in separately authorized private systems or services:

- real customers, suppliers, facilities, laboratories, samples, lots, and contracts;
- protected technical thresholds, methods, measurements, and patent-sensitive work;
- ownership and control analysis using nonpublic records;
- source alternatives, qualification plans, capacity, pricing, schedules, and economics;
- customer-specific risk priorities, mission weighting, ROI, ROO, and commercial strategy;
- real evidence graphs, monitoring, actions, decisions, outcomes, and continuing assurance.

The public repository may demonstrate the method but must not expose those records or the
proprietary logic that creates customer-specific advantage.

## Permanent No-Go Decisions

Do not:

- create a competing public `critical-supply-chain-assurance` repository;
- create a second Materials-to-Mission schema authority in another repository;
- publish real supplier, customer, laboratory, facility, pricing, capacity, vulnerability,
  restricted, export-controlled, classified, or patent-sensitive information;
- describe the toolkit as a compliance engine, certification authority, automatic FOCI
  adjudicator, waiver authority, or official filing system;
- convert missing evidence into a low-risk score;
- let a composite score average away a triggered critical condition;
- let automation approve, qualify, terminate, waive, or close a consequential decision;
- publish universal ROI, ROO, savings, production, adoption, or mission-performance claims;
- build a hosted backend, broad supplier database, or autonomous recommendation engine
  without separate evidence, authority, and security justification;
- add organization or enterprise-team ceremony to the current personal-account demonstration.

## Public UX Direction

Public UX should remain calm, minimal, local, and decision-oriented.

A user should quickly understand:

1. what decision is being considered;
2. what evidence supports it;
3. what remains unknown or contradictory;
4. what condition blocks advancement;
5. what action is required;
6. who owns the action and final disposition;
7. what proves closure and triggers reassessment.

Future interfaces should use direct status language, non-color cues, keyboard support,
accessible structure, clear error recovery, and compact executive views without hiding the
complete analyst record.

## Release Rule

No future public release is justified merely because an idea exists in this register. Every
change requires an evidence-backed issue, bounded branch, tests, public-boundary review,
exact-head validation, reviewed merge, and release decision proportionate to its risk.
